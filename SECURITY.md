# Security review — 2026-10-06

This review covered the application source, local vendor bundle, configuration, build output, claim and email flows, analytics, and both Docker Compose files. Confirmed issues were fixed and regression-tested. It does not certify that the application has no vulnerabilities, and it does not establish the security of the deployed DNS, Traefik host, email account, or analytics dashboards.

## Shared-link and QR extension

`DANA_REWARD_LINK` optionally enables a shared link for all new verified emails. It remains server-only until a valid claim and is validated against the HTTPS DANA host allowlist. One claim per normalized email is persisted with its original link; repeated claims and configuration changes preserve the first reward. Existing exclusive allocations remain recoverable. A blank setting retains imported inventory for new claimants.

QR encoding runs locally from a pinned, bundled encoder. No QR service receives the reward. The clickable URL below uses a native button with link semantics and `noopener,noreferrer`, retaining the protection against outbound-anchor analytics. Reset removes both QR and link content. Dense/failed QR rendering leaves the clickable link available.

The shared link can be copied or forwarded after reveal. The app's per-email claim ledger cannot enforce one redemption per DANA account, prevent link sharing, or establish remaining balance/expiry. Those controls belong to DANA. Database backups and the private environment now both contain redeemable URLs. See [VALIDATION.md](VALIDATION.md) for the extension's verification results.

## Meta Conversions API extension

Meta delivery is opt-in and server-only. Pixel ID and access token must both be configured; neither the token nor test event code is returned to browsers. The form exposes only an enabled boolean and requests fresh, versioned permission that explicitly covers Meta ad measurement. A scoped grant ID binds retry queues to the permission that created them, preventing reuse of analytics-only consent and replay after withdrawal/regrant in another tab.

Only consented page views and newly persisted, cookie-bound OTP claims become Meta events. Client success telemetry cannot manufacture claim conversions; recovered claims produce no new conversion. The outbound payload contains a fixed page URL plus IP/user-agent matching metadata, without email/hash, OTP, reward, referrer, query strings or arbitrary properties. Forwarded IPs follow the same trusted-proxy rules as rate limits. No Meta browser SDK is loaded, and no additional CSP origins are allowed.

Requests use a fixed HTTPS Graph endpoint, a server-only Bearer header, redirect refusal, a five-second timeout and a 16 KiB response limit. Delivery has bounded concurrency and deduplication state; diagnostics expose counts only through the existing operator report. There is no persistent Meta queue, metadata journal or server retry. Provider failures cannot break claims; outages/capacity limits can lose events, and deduplication does not survive process restart. Withdrawal cannot recall requests already sent. Details and account verification steps are in [README.md](README.md#meta--facebook-integration).

## Findings and changes

| Finding | Exposure before this review | Remediation and evidence |
| --- | --- | --- |
| Report data lacked application authorization | Direct access to the app on `edge`, or another deployment route, could read the report and event export. Traefik exclusions alone were insufficient. | Live report pages and APIs return 404 unless operator credentials are configured; then every request requires Basic authentication. Tests cover direct, encoded, normalized, GET and HEAD paths, wrong credentials, and public analytics module access. |
| Local inbox dependency was vulnerable | Mailpit v1.26 was affected by cross-origin WebSocket attacks against localhost inboxes. | Updated to Mailpit v1.31.4 and pinned its pulled image digest. The maintainer documents both the [original issue](https://github.com/axllent/mailpit/security/advisories/GHSA-524m-q5m7-79mm) and the [later bypass fixed in v1.30.6](https://github.com/axllent/mailpit/security/advisories/GHSA-8r62-w5wh-fc5m). |
| Grovs bypassed the property privacy filter | The real SDK sent current `Grovs`/`linksquared` URL attribution and persisted paths independently of custom event sanitization. | A maintained vendor patch adds `captureDeepLinks: false` and removes paths from queued outgoing events. Tests execute the bundled SDK with synthetic URLs/storage and intercepted transports. Original and patched hashes plus reproduction instructions are in `public/vendor/grovs/`. Campaign deep-link attribution is disabled. |
| Consent withdrawal did not reach other tabs | A previously consented tab could keep sending after another tab revoked consent. | Storage-event synchronization and fail-closed checks before initialization, delivery, retries and beacons stop providers and discard queued events. Tests cover withdrawal across trackers, expired/cleared consent, initialization races, and retries. Requests already transmitted cannot be recalled. |
| Analytics ingestion could exhaust collection | Anonymous batches could permanently hit the journal cap, while pending writes could retain unbounded batches. | Per-client event and HTTP budgets, a bounded identity table, at most 64 pending batches of 20 events, and rolling retention. Tests cover saturation, concurrent deduplication, atomic rotation, restart, and recovery after write failures. Client events remain untrusted telemetry. |
| Proxy traffic shared a single client budget | One visitor could exhaust the proxy IP's code/claim quota for other visitors. | Forwarded addresses are used only when the immediate peer is explicitly trusted. The chain is walked from right to left, stopping at the first untrusted address. Tests reject spoofing from untrusted peers and malformed chains. Traefik deployment requires an explicit proxy IP/CIDR. |
| Code requests disclosed participation and recent activity | Exhausted stock returned different results for existing claimants; email throttles disclosed other browsers' request activity. | Stock is checked only after a valid OTP. Cross-session throttles return opaque accepted responses with decoy challenges that can never allocate rewards. Tests cover guesses, lockout, expiry, repeated requests, supersession, quotas, and recovery. Timing and provider failure differences are still a limitation below. |
| Reward links could reach automatic click analytics | With GA4 outbound-click measurement enabled, the reward URL in an anchor could be collected outside the explicit event filter. This was conditional on dashboard configuration, not observed live leakage. | The reward is opened through a button with a validated HTTPS DANA URL and `noopener,noreferrer`; no reward URL is placed in an anchor. GA4 automatic collection still requires dashboard verification. |
| HTTP defenses and runtime versions needed improvement | No host allowlist, framing protection, CSP, or explicit body/header deadlines; live session cookies lacked a host prefix; Node's declared minimum predated security fixes. | Added Host/Origin validation, `__Host-` live cookies, CSP, framing protection, HSTS in live mode, body/header/time limits and bounded HTTP throttling. Supported Node 22 minimum is 22.23.2; the image pins 22.23.3 and its digest. See the [Node security release](https://nodejs.org/en/blog/vulnerability/july-2026-security-releases). |

The app containers run as a non-root app user, with root-owned source, a read-only root filesystem, dropped capabilities, no-new-privileges, a PID limit, and writable private data volumes. These controls reduce impact; they are not evidence that arbitrary code execution is impossible.

## Validation performed during the security audit

- `npm test`: **99 passed**, including the actual vendored SDK under stubbed transports, allocation races, OTP/session binding, provider redaction, report access control, proxy spoofing, and storage abuse/recovery.
- `npm run check` and `npm run build`: passed.
- Compose rendering and required-variable checks use synthetic credentials, including app security configuration and trusted-proxy validation. No real credential values are printed.
- Docker fetched the pinned patched images and built `dana-kaget:security-audit`. An isolated container with no network access or published ports passed HTTP API, operator authentication, cookie/header, host validation, Node version, non-root, read-only source, private writable volume and `.env` exclusion checks. Test containers and volumes were removed.
- A pattern-based source scan found no actual credentials in nonignored source files. The private `.env` is ignored and mode 0600. This directory has no Git history to scan. No full OS-package image vulnerability scanner was available.
- Browser smoke testing was blocked by the browser's automatic security check because the admin-enforced policy could not be verified. No alternative browser-control route was used. Visual behavior, external widget loading under CSP, and browser popup behavior are therefore not newly verified.

## Deployment requirements

1. Set `APP_HOST=dana.skytek.id`, the production Turnstile keys for that hostname, the full Kirim.Email credentials/sender, and a stable random `CLAIM_SECRET` in the private environment file.
2. Set `TRUSTED_PROXY_CIDRS` to the actual Traefik address(es), preferably exact `/32` or `/128` entries. Keep the proxy address stable. Do not trust an entire shared network containing unrelated containers. Traefik must also reject untrusted forwarded headers: do not enable `forwardedHeaders.insecure`; configure upstream trusted IPs only if a real upstream proxy exists. See [Traefik's forwarded-header settings](https://doc.traefik.io/traefik/reference/install-configuration/entrypoints/#forwarded-headers).
3. Live reports are disabled by default. To enable them, set `REPORTS_USER` and a randomly generated `REPORTS_PASSWORD` of at least 32 characters. Use HTTPS. These credentials are separate from email-provider credentials and are never returned by `/api/config`.
4. Keep GA4 Enhanced Measurement and automatic user-provided data collection disabled for this property, and verify the dashboard settings. The repository cannot establish their state. See [Google's Enhanced Measurement documentation](https://support.google.com/analytics/answer/9216061).
5. Rebuild and deploy the corrected source and pinned images; verify TLS, actual client-IP propagation, authenticated reports, and a synthetic end-to-end claim on the deployment. This review did not deploy the public stack or send live email.

## Remaining limits

- Email request acceptance is not proof of provider acceptance or inbox delivery. A different browser requesting an address during its delivery quota may receive an accepted response without new mail. Real provider latency and failures can still differ from suppressed requests, so recent activity is not guaranteed to be indistinguishable by timing. Previous participation is no longer exposed by stock responses.
- These limits bound individual clients and local resource use. They are not distributed denial-of-service protection. The service and event journal assume one app writer/instance; horizontally scaled deployment needs shared rate limiting and coordinated persistence.
- Old events are discarded when retention rotates from over 100,000 to the newest 90,000. Reports cover retained telemetry, not the complete lifetime of a campaign. IDs can be accepted again after they leave retention. Client-generated success events are never an authoritative reward ledger.
- Third-party scripts, account/dashboard configuration, image packages, host administration, backup access, and newly published vulnerabilities need ongoing review. Patch provenance does not substitute for upstream maintenance.
- Reward inventory and backups contain redeemable values in plaintext. They require restricted storage and backup access. One reward per normalized email is not one reward per person, and this app cannot verify redemption in DANA.
